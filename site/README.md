# Telex website

The website for Telex: Next.js 16 (App Router), plain CSS with the app's color tokens, no other
dependencies. Sixteen prerendered pages (home, features, live demo, keyboard, performance, accessibility,
screenshots, download, changelog, roadmap, FAQ, about, history, privacy, security, license), light and dark, with a download button
that finds the newest installer on its own, and a live demo that runs the app's own interface.

```
npm install
npm run dev        # http://localhost:3000
npm run build      # what Vercel runs
npm run posters    # refresh responsive hero derivatives (also checked before every build)
npm run screens    # retake the screenshots from ../ui (needs Edge or Chrome)
npm run demo       # rebuild the live demo from ../ui into public/demo-app
npm run icons      # rebuild every app and site icon from ../brand
npm run themes     # measure the app's themes again into lib/themes.json (the accessibility page)
```

## Where things are

- `lib/pages.ts`: every page's address, menu label, title, description and link-preview line.
  The header, footer, sitemap, breadcrumbs and preview images all read it. Add a page here first.
- `lib/site.ts`: name, keywords, site URL, contact address, the GitHub repo that holds releases.
- `lib/content.ts`: features, feature rows, shortcuts and tips, screenshot captions, the versions
  (the changelog), roadmap, FAQ, the live demo's cards, and the lines the telex tape punches. Keep
  it true to the app; update the roadmap when a step lands.
- `/performance`: measured desktop timings and whole-process memory/CPU comparisons. `lib/performance.ts`
  reads `public/benchmarks/windows-100k.json`, generated by the repository's benchmark scripts.
  The home page's figures use the same data and the live release's Windows installer size.
  Reproduction and comparison rules are in `../docs/performance.md`; never hand-edit a flattering figure.
- `/security`: Privacy & security, linked beside downloads and in the footer. Each protection
  links to source; check results link to the public Security checks workflow. Keep limitations
  and open findings visible. `../docs/security.md` describes the checks and evidence; never
  assume a passing result, an independent audit, or installer verification that has not happened.
- `lib/versions.ts`: what the site says about something built for a version (see below).
- `lib/release.ts`: reads the GitHub releases that have an `.exe` or `.msi`, with their AppImage
  and .deb (checked hourly). `lib/known-release.ts`: the newest release, for when GitHub can't be
  asked while the site is built (see "Making the download button live").
- `lib/seo.ts`: per-page metadata and the structured data (breadcrumbs, app, website, FAQ).
- `lib/theme.ts`: the light/dark choice. It is `data-theme` on `<html>`, saved in localStorage
  and set before the first paint by the script in `app/layout.tsx`; tokens are in `app/globals.css`.
- `app/<page>/page.tsx`: the subpages. Shared pieces are in `components/`, each with a CSS module.
- `/history`: an illustrated history of telex, email and related messaging. `lib/history.ts` holds
  its references, milestones and glossary; `components/HistoryLab.tsx` provides timeline filters,
  an ITA2 workbench (using the shared encoder) and message journeys. The generated hero image in
  `public/history/` is explicitly illustrative; `asset-notes.json` records its prompt and provenance.
  `components/NightShift.tsx` adds a fictional three-line dispatch game, with a 90-second shift,
  untimed practice, optional synthesized sound and a browser-local personal best. `lib/night-shift.ts`
  holds its game rules; transmission timing uses the shared ITA2 encoder at 50 baud. Generated
  game artwork and its prompt are in `public/history/night-shift.webp` and `night-shift-asset.json`.
  Run `node --test scripts/night-shift.test.mjs` for the dispatch, timing and scoring checks.
  Its WebGL scene adds layered camera depth, window rain and lamp flicker with a static fallback,
  reduced-motion support and an atmosphere switch. The local audio engine synthesizes mechanical
  impacts, a 50-baud printer, a motor, rain and a metal bell. Delivered telegrams track first-view
  reaction time, active writing time, five-character WPM, insertion accuracy and queue delay.
- `public/screens/`: screenshots, `<scene>-light.webp` and `<scene>-dark.webp` (lossless), 1280×800 at 2×.
- `public/posters/` and `lib/hero-posters.json`: fingerprinted AVIF/WebP hero derivatives, generated
  by `scripts/posters.mjs` from the inbox screenshots. Keep these files together in Git. The
  prebuild step checks the source hashes and regenerates missing/outdated derivatives.
- `app/**/opengraph-image.png`: one link preview per page, made by `npm run screens`.
  Pages can set `ogImage` in `lib/pages.ts` to use editorial artwork instead of a screenshot.

### Night Shift's shared leaderboard

Apply `supabase/migrations/20261013_night_shift.sql` to the chosen Supabase project (SQL editor or
`supabase db push`). Set three server-only values in ignored `site/.env.local` for development and
in the Vercel project's environment for hosting; `.env.example` lists them:

- `SUPABASE_URL`: the project's `https://….supabase.co` address.
- `SUPABASE_SECRET_KEY`: its secret key (the legacy `service_role` key is also accepted as
  `SUPABASE_SERVICE_ROLE_KEY`).
- `NIGHT_SHIFT_SIGNING_SECRET`: a random value of at least 32 characters, different from the key,
  e.g. `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. It signs
  scored sessions and keys the rate-limit hashes. Changing it voids shifts in progress, nothing else.

The site's API issues signed seeds and replays individual typing and selection events to calculate
scores and timings itself. A run can be published once (its signed session UUID is the primary key).
Full 90-second shifts and shifts ending after three misses are eligible; practice and manual early
finishes are excluded. Public rows contain the chosen operator name and derived statistics, not the
typing log. The database permits only the server role to read/insert; browsers never receive its key.
The board shows one best run per operator name for the selected score, speed or reaction ranking,
with all-time, rolling seven-day and UTC-today filters. Names are aliases, not authenticated identities.

Against scripted runs and spam (the game is deterministic from its seed, and the same-origin check
stops other sites, not scripts):

- The replay asks for a person's pace (`HUMAN` in `lib/night-shift-ranking.ts`): at least 0.1 s from
  a telegram appearing to its first key, at most 20 keystrokes in any second, few keystrokes under
  30 ms apart, and 250 WPM over the shift.
- Per network (an IPv4 address or IPv6 /64): 40 scored sessions an hour, 10 published runs an hour
  and 40 a day. Counted in Supabase (`night_shift_limits`, `night_shift_take()`) under a keyed hash
  of the address, never the address itself; rows go after two days. If Supabase can't be reached,
  scored play and publishing are refused (the game still works).
- Operator names (`lib/night-shift-names.ts`): 2–20 letters and numbers with single spaces or
  `. _ ' -` between them, one alphabet per name (no Latin/Cyrillic lookalikes), and a basic English
  and Polish word filter that also catches leetspeak and spaced-out spellings.
- The board's GET is cached at Vercel's edge for 30 seconds (`s-maxage=30`) and answers only its six
  real queries, so made-up parameters can't bypass the cache. A run just published is added to the
  board in the browser until the cache catches up.

A patient script that types at human speed can still publish. This is a casual game leaderboard,
not proof of a human competitor; remove a row in Supabase's table editor if needed.

Without storage configuration, the game keeps working and clearly shows the online board as
unavailable. No placeholder opponents or pretend online scores are inserted.

## Versions: what is out and what is coming

Features, points, shortcuts, tips, screenshots and roadmap steps carry a fixed `since` version
(for example `V095` for 0.9.5). Keep that version unchanged after release. Until GitHub has a
release that new, the site marks them "Coming"; once published they turn into "New" within the
hour, with no redeploy (`lib/versions.ts`, `components/Since.tsx`). The newest entry in `versions`
drives the hero and What's new. When a newer minor version is out, older badges go away.

After a release:

1. Its entry in `versions` (`lib/content.ts`) already says what it brought; give it its date.
2. As features for the next version land, add its entry (title, summary, points and `highlights`
   for the home page), and mark only its new features with that version. Keep released entries fixed.
3. Retake the screenshots (`npm run screens`) and rebuild the demo (`npm run demo`).
4. Put the new release in `lib/known-release.ts` (version, date, file sizes from GitHub).

The changelog page merges `versions` with the releases on GitHub: dates and files come from GitHub,
and a release the site doesn't describe yet still shows, with a link to its notes.

## The live demo

`/demo` shows the app itself in a frame. `public/demo-app/` is a copy of `../ui` (index.html,
app.js, i18n.js, boot.js, the style sheets and fonts) plus `demo/backend.js`, a stand-in for Tauri
and the Rust core that answers every `invoke` from the English demo mailbox
(`scripts/demo-mailbox.json`), in memory. `npm run demo` (`scripts/demo.mjs`) builds that folder;
run it after UI changes, like `npm run screens`, and commit the result (Vercel builds only this
folder). The screenshots use the same backend with the clock stopped at 10.10.2026 09:30; the live
demo moves the mailbox's dates so that its "today" is the visitor's.

`components/DemoFrame.tsx` starts it in the page's theme (`?theme=light|dark`; `?lang=en|pl` works
too), shows the inbox screenshot until the app has drawn itself, and puts the app's window title in
the frame's title bar. When the visitor switches the site between light and dark, it posts
`{type: 'telex-demo-theme', theme}` to the frame; `demo/backend.js` sets the theme and emits the
app's own `settings-changed`, so the running app follows without a restart. Above the frame (and
on the home page's demo band) are three first tries, `demoFirst` in `lib/content.ts`; keep them
true to the mailbox. `next.config.ts` lets only this site frame `/demo-app/` and keeps it out of
search results. Nothing in the demo talks to the network: sending moves mail to Sent, and
attachments can be added but not opened.
Saved searches, rule previews, copy actions, optional threads and toolbar layouts work against
the in-memory mailbox. The scam report and the spam filter's note are fixed illustrative fixtures,
not the Rust scanner or filter; Mark as spam and Not spam move mail but learn nothing; automatic
forwarding cannot send real mail. Keep these limits visible on the demo and FAQ pages.

## The footer

`components/TelexTicker.tsx` is the live telex bar: it punches each line of `ticker` (in
`lib/content.ts`) into paper tape in real ITA2 code (`lib/ita2.ts`, with the figure/letter shift
columns) at 50 baud, the speed of a telex line, and prints it underneath. It runs only while it is
on screen, has a Pause button, and stands still for people who ask for reduced motion. Below it,
`components/DotMatrix.tsx` draws TELEX as teleprinter dots; pointing at dots lights them up.

## Landing performance

Phones below 900px use device-native fonts, with no font downloads. Desktop keeps the locally
served Plex families with optional display; no unconditional font preload competes with the
first paint. The hero uses a theme-matched responsive AVIF with WebP fallback, precomputed so
a cold visit does not wait for the image optimizer. Gallery screenshots keep their original
quality. The live demo's code and iframe load only after activation.

Long home sections and the footer use `content-visibility: auto` on screen. Their content stays
in server HTML, remains available to search/accessibility and prints normally. The tape pauses
offscreen; repeating SVG dots use patterns/paths instead of hundreds of elements. Client
components receive only their needed content, and page links prefetch on hover, focus or touch
instead of fetching every visible link on initial load. Full-page prefetching is sufficient for
these prerendered routes; hourly release revalidation remains enabled.

Next's experimental `cssChunking: 'graph'` prevents unrelated subpage styles being merged into
the landing's initial CSS. This is covered by production-build browser checks; recheck both
loading and styling when upgrading Next. Do not enable global CSS inlining: it duplicates the
styles in HTML/RSC and measured worse here.

The 20 October local production-build audit reached 100 in all four Lighthouse categories on
three cold mobile runs and one desktop run over HTTP/2 + Brotli. A direct HTTP/1.1 + gzip
`next start` mobile check scored 98. These transport environments differ; verify the deployed
domain separately. Method, limitations and measurements are in
[`../docs/site-seo-audit-2026-10-20.md`](../docs/site-seo-audit-2026-10-20.md).

## SEO

Each page exports `pageMetadata(pages.x)` (`lib/seo.ts`): title, description, canonical URL, Open
Graph and Twitter cards; its preview image is the `opengraph-image.png` next to it. Subpages get
a visible breadcrumb and a BreadcrumbList; the home and download pages describe the app
(SoftwareApplication, with a zero-price offer for the free preview and no invented ratings),
the FAQ page its questions (FAQPage). Next.js generates `robots.txt`,
`sitemap.xml` (every page, screenshots as image entries) and `manifest.webmanifest` from `app/`. With
a custom domain attached, the `*.vercel.app` address answers with `X-Robots-Tag: noindex`, so
only your domain gets indexed. The sitemap omits `lastmod` until actual page-update dates are
tracked; rebuilding the site does not mean every page's content changed.

Canonical URLs default to `https://telexmail.app` in every environment, including local builds
and previews. Only `NEXT_PUBLIC_SITE_URL` overrides that origin; a Vercel deployment alias is
never chosen automatically. Legacy `/screens/*.png` URLs are internally rewritten to WebP so
cached pages and old `/_next/image` requests keep working.

The accessibility page sends theme summaries and links in its initial HTML. Its detailed
contrast tables load on opening a disclosure, from prerendered
`/accessibility/contrast/<theme>.json` evidence files (intentionally `noindex`, outside the
sitemap). The JSON links also work without JavaScript. This keeps the page below the audit
crawler's 600 KB HTML limit rather than sending all 2,170 measurement rows twice in HTML/RSC.
Run `npm run test:seo` for the canonical-origin and JSON-LD script-escaping regressions.
After `npm run build`, run `npm run check:seo` to verify every public page's metadata, headings,
canonical, sitemap inclusion, JSON-LD, original images and the 600 KB HTML budget.

### SEO audits through Vercel

If a crawler receives `429` with `X-Vercel-Mitigated: challenge` or renders a page titled
"Vercel Security Checkpoint", check the project's **Firewall** traffic events while starting
a fresh scan. This is an access failure; compare source and rendered HTML only after the
renderer reaches the actual page. Both the crawler and the separate rendering service need access.

Get the confirmed outbound IPs/CIDRs for both services from SEOMaster; the report does not
provide them. The rendering service's DNS address is not necessarily its outbound IP.
In **Firewall → ⋯ → Configure → Add New… → Rule**, create **SEOMaster audit** with all of:

- **Hostname → Equals → `telexmail.app`**
- **IP Address → Is any of → the confirmed crawler and renderer outbound IPs/CIDRs**
- **Method → Is any of → `GET`, `HEAD`**
- **Then → Bypass**

Combine the conditions with **AND**, put the rule above any custom challenge/deny rules,
then **Save Rule → Review Changes → Publish**. This takes effect without a site redeploy.
Keep Bot Protection enabled for other traffic. A public `x-seomaster-crawler` marker or a
user-agent string alone does not authenticate the scanner. If events identify a system-level
mitigation instead, custom bypass rules do not bypass it; use Vercel's System Bypass Rules
only for the confirmed sources. See [custom rules](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules),
[bot protection](https://vercel.com/docs/vercel-firewall/vercel-waf/managed-rulesets) and
[system bypass rules](https://vercel.com/docs/vercel-firewall/vercel-waf/system-bypass-rules).

After publishing the rule and deploying code changes, rerun the full scan. The scanner should
receive the real `200` HTML, read all 16 public sitemap URLs and load the page assets; the
rendered title must be the page's title. Verify actual Googlebot access separately with
Search Console's URL Inspection live test, and repeat PageSpeed against the current deployment.

## Counting downloads and copies, and /stats

What the app sends and why it is built this way is in `../docs/counting.md`. On the site:

- `app/api/count/route.ts` takes the app's daily count (only from copies whose user said yes):
  JSON only, exactly the app's seven keys (`parsePing` in `lib/count.ts`), at most 200 a day per
  network (a keyed hash in Night Shift's `night_shift_limits`, gone after two days). It adds one
  to a sum per UTC day, version, system, language and first month (`telex_count_days`); no
  request is stored.
- `app/api/downloads/snapshot/route.ts` is called by Vercel's cron (`vercel.json`, daily at
  00:05 UTC) and stores GitHub's download totals per file for the day (`telex_download_totals`),
  so downloads per day can be worked out. Opening /stats takes the same snapshot.
- `app/stats/route.ts` is the owner's private page: downloads per release and kind, per day,
  update checks (latest.json fetches), copies active today, this week and this month, new ones,
  versions, systems, languages and cohorts. It answers 404 until `STATS_PASSWORD` (12+
  characters) is set; the browser asks for it (any user name), ten wrong tries an hour.

Setting it up: apply `supabase/migrations/20261017_telex_count.sql` (after the Night Shift one,
whose limiter it uses) and set `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `STATS_PASSWORD` and
`CRON_SECRET` in the Vercel project (`GITHUB_TOKEN` optional). Tests: `node --test
scripts/count.test.mjs`.

## Security, analytics and plain-text files

- `next.config.ts` sends security headers in production: a Content Security Policy (this site
  only; inline scripts allowed because static Next.js pages need them), HSTS, nosniff, DENY
  framing, a strict referrer policy, Permissions-Policy and COOP. Previews also allow Vercel's
  toolbar. If you add a third-party script or font, add its origin to the CSP there.
- Vercel Web Analytics (`<Analytics />` in `app/layout.tsx`, enabled only on Vercel) counts page views without cookies;
  its script comes from the site itself (`/_vercel/insights`). Turn it on in the Vercel project
  under **Analytics**, or the script answers 404. The privacy page describes it.
- `app/llms.txt/route.ts` and `app/.well-known/security.txt/route.ts` are generated from the
  same data as the pages at build time. security.txt expires a year after the build, so deploy
  at least once a year.
- Text colors are checked against WCAG AA (4.5:1). `--faint` is the lightest text allowed;
  don't make it lighter.
- The accessibility page shows the app's themes as measured by `../scripts/check-contrast.mjs`
  (`lib/themes.json`, from `npm run themes`) and one screenshot per theme
  (`public/screens/theme-<id>.webp`, from `npm run screens themes`). Redo both after a color in
  `../ui/themes.css` changes.

## Screenshots

`npm run screens` opens `../ui/index.html` in headless Edge with the live demo's stand-in for
Tauri (`demo/backend.js`), answering from the English demo mailbox (`scripts/demo-mailbox.json`:
two accounts with identities, rules, conversations, attachments, an HTML newsletter, and the mail
that "arrives" in the live demo), plays a short scene for each shot (open a reply, type in the
quick filter, …) and saves light and dark versions. The clock is fixed at 10.10.2026 09:30 so list
dates stay the same. Scenes are at the top of `scripts/screens.mjs`. The stand-in copies what the
core does for lists and filters (`list.rs`), replies (`drafts::start`), HTML mail (`html::render`,
`colors.rs`) and rules (`filters.rs`); when those change visibly, change it too. (The core's own
`sample.json` is Polish and only for its tests.)
`npm run screens reply og` retakes only those; `og` makes the preview image of every page in
`lib/pages.ts` (its `ogTitle` next to its `ogScreen`).
Use `npm run screens -- og:history` to regenerate only the history page's editorial preview.

## Deploying on Vercel

1. Import the GitHub repo in Vercel and set **Root Directory** to `site`. Everything else is
   detected (Next.js, `npm install`, `npm run build`).
2. Add `telexmail.app` under **Settings → Domains**. Canonical links, the sitemap and link previews
   use this domain by default. Set `NEXT_PUBLIC_SITE_URL` explicitly if the public domain changes.
3. Pushes to `main` that don't touch `site/` are skipped (`vercel.json`, `ignoreCommand`), so app
   commits don't rebuild the website. The same check cancels **Redeploy** of a commit already
   deployed (it starts, then disappears), so after changing environment variables, push a commit
   that touches `site/` to build with them.

Optional environment variables:

| Variable               | Default               | Use                                           |
|------------------------|-----------------------|-----------------------------------------------|
| `NEXT_PUBLIC_SITE_URL` | `https://telexmail.app` | Override the canonical origin                 |
| `TELEX_RELEASES_REPO`  | `lucco669/telexmail`  | Repo whose GitHub Releases hold the installers |
| `GITHUB_TOKEN`         | –                     | Only raises GitHub's API rate limit           |
| `NEXT_PUBLIC_CONTACT_EMAIL` | `admin@telexmail.app` | Overrides the contact address on the privacy page |

## Making the download button live

Until a release exists the button says "Coming soon". It switches to a direct download link as
soon as the releases repo has a published release with a Tauri installer attached
(`Telex_<version>_x64-setup.exe`, plus the `.msi` as a second link), within an hour, with no
redeploy. The repo has to be **public**: visitors can't download assets from a private repo's
releases. If `telexmail` stays private, make a public repo just for installers (for example
`telex-releases`) and set `TELEX_RELEASES_REPO` to it.

The release workflow makes a **draft** release, and GitHub hides drafts from everyone else, the
site included: the button stays "Coming soon" until you press **Publish release** on GitHub.
"Within an hour" means the first visit after the hour starts a rebuild of the page in the
background (`cacheLife` in `lib/release.ts`: revalidate after an hour, never expire), and the
visits after that see the new release. Set `GITHUB_TOKEN` in Vercel to be safe: without it the
lookup shares GitHub's limit of 60 requests an hour with everything else on Vercel's IP address.

When GitHub can't be asked (refused, unreachable), the lookup throws on the live site: the page's
background refresh fails, Next.js keeps serving the page with the last good answer and tries again
on the next visit, so a failure never turns the downloads into "Coming soon". At build time and in
`npm run dev` there is no earlier answer, so the site offers `lib/known-release.ts` (with a note on
the download page that it couldn't check for a newer one), or, if that is empty, links to GitHub's
newest-release page. "Coming soon" is only for when GitHub answers that nothing is released.
