# Telex website

The website for Telex: Next.js 16 (App Router), plain CSS with the app's color tokens, no other
dependencies. Fourteen prerendered pages (home, features, live demo, keyboard, performance, accessibility,
screenshots, download, changelog, roadmap, FAQ, about, history, privacy), light and dark, with a download button
that finds the newest installer on its own, and a live demo that runs the app's own interface.

```
npm install
npm run dev        # http://localhost:3000
npm run build      # what Vercel runs
npm run screens    # retake the screenshots from ../ui (needs Edge or Chrome)
npm run demo       # rebuild the live demo from ../ui into public/demo-app
npm run icons      # rebuild every app and site icon from ../brand
npm run themes     # measure the app's themes again into lib/themes.json (the accessibility page)
```

## Where things are

- `lib/pages.ts`: every page's address, menu label, title, description and link-preview line.
  The header, footer, sitemap, breadcrumbs and preview images all read it. Add a page here first.
- `lib/site.ts`: name, keywords, site URL, contact address, the GitHub repo that holds releases.
- `lib/content.ts`: features, feature rows, shortcuts and tips, screenshot captions, the versions
  (the changelog), roadmap, FAQ, the live demo's cards, and the lines the telex tape punches. Keep
  it true to the app; update the roadmap when a step lands.
- `/performance`: measured desktop timings and whole-process memory/CPU comparisons. `lib/performance.ts`
  reads `public/benchmarks/windows-100k.json`, generated by the repository's benchmark scripts.
  The home page's figures use the same data and the live release's Windows installer size.
  Reproduction and comparison rules are in `../docs/performance.md`; never hand-edit a flattering figure.
- `lib/versions.ts`: what the site says about something built for a version (see below).
- `lib/release.ts`: reads the GitHub releases that have an `.exe` or `.msi`, with their AppImage
  and .deb (checked hourly). `lib/known-release.ts`: the newest release, for when GitHub can't be
  asked while the site is built (see "Making the download button live").
- `lib/seo.ts`: per-page metadata and the structured data (breadcrumbs, app, website, FAQ).
- `lib/theme.ts`: the light/dark choice. It is `data-theme` on `<html>`, saved in localStorage
  and set before the first paint by the script in `app/layout.tsx`; tokens are in `app/globals.css`.
- `app/<page>/page.tsx`: the subpages. Shared pieces are in `components/`, each with a CSS module.
- `/history`: an illustrated history of telex, email and related messaging. `lib/history.ts` holds
  its references, milestones and glossary; `components/HistoryLab.tsx` provides timeline filters,
  an ITA2 workbench (using the shared encoder) and message journeys. The generated hero image in
  `public/history/` is explicitly illustrative; `asset-notes.json` records its prompt and provenance.
- `public/screens/`: screenshots, `<scene>-light.webp` and `<scene>-dark.webp` (lossless), 1280×800 at 2×.
- `app/**/opengraph-image.png`: one link preview per page, made by `npm run screens`.
  Pages can set `ogImage` in `lib/pages.ts` to use editorial artwork instead of a screenshot.

## Versions: what is out and what is coming

`NEXT` in `lib/content.ts` is the version being finished. Features, points, shortcuts, tips,
screenshots and roadmap steps built for it carry `since: NEXT`. Until GitHub has a release that new,
the site marks them "Coming in 0.5" (the roadmap step is in progress, the hero and the home page's
What's new say "Coming"); once the release is published they turn into "New in 0.5" within the
hour, with no redeploy (`lib/versions.ts`, `components/Since.tsx`). When a newer minor version is
out, the badges go away by themselves.

After a release:

1. Its entry in `versions` (`lib/content.ts`) already says what it brought; give it its date.
2. Set `NEXT` to the version after it, and add that version's entry (title, summary, points and
   `highlights` for the home page) as its features land.
3. Retake the screenshots (`npm run screens`) and rebuild the demo (`npm run demo`).
4. Put the new release in `lib/known-release.ts` (version, date, file sizes from GitHub).

The changelog page merges `versions` with the releases on GitHub: dates and files come from GitHub,
and a release the site doesn't describe yet still shows, with a link to its notes.

## The live demo

`/demo` shows the app itself in a frame. `public/demo-app/` is a copy of `../ui` (index.html,
app.js, i18n.js, boot.js, the style sheets and fonts) plus `demo/backend.js`, a stand-in for Tauri
and the Rust core that answers every `invoke` from the English demo mailbox
(`scripts/demo-mailbox.json`), in memory. `npm run demo` (`scripts/demo.mjs`) builds that folder;
run it after UI changes, like `npm run screens`, and commit the result (Vercel builds only this
folder). The screenshots use the same backend with the clock stopped at 10.10.2026 09:30; the live
demo moves the mailbox's dates so that its "today" is the visitor's.

`components/DemoFrame.tsx` starts it in the page's theme (`?theme=light|dark`; `?lang=en|pl` works
too), shows the inbox screenshot until the app has drawn itself, and puts the app's window title in
the frame's title bar. When the visitor switches the site between light and dark, it posts
`{type: 'telex-demo-theme', theme}` to the frame; `demo/backend.js` sets the theme and emits the
app's own `settings-changed`, so the running app follows without a restart. Above the frame (and
on the home page's demo band) are three first tries, `demoFirst` in `lib/content.ts`; keep them
true to the mailbox. `next.config.ts` lets only this site frame `/demo-app/` and keeps it out of
search results. Nothing in the demo talks to the network: sending moves mail to Sent, and
attachments can be added but not opened.

## The footer

`components/TelexTicker.tsx` is the live telex bar: it punches each line of `ticker` (in
`lib/content.ts`) into paper tape in real ITA2 code (`lib/ita2.ts`, with the figure/letter shift
columns) at 50 baud, the speed of a telex line, and prints it underneath. It runs only while it is
on screen, has a Pause button, and stands still for people who ask for reduced motion. Below it,
`components/DotMatrix.tsx` draws TELEX as teleprinter dots; pointing at dots lights them up.

## Logo and icons

The logo lives in `../brand`: `telex-mark.svg` for 48 px and up, `telex-mark-small.svg` (no faint
dot grid, bigger dots) for 32 px and below. `npm run icons` renders both with sharp into:

- the desktop app: `src-tauri/icons/` (PNG sizes and a 16–256 px `icon.ico`),
- the site: `app/favicon.ico`, `app/icon.svg`, `app/apple-icon.png` (full-bleed, iOS rounds it),
  `public/icon-192.png`, `public/icon-512.png`, `public/icon-maskable-512.png` (for Android).

The header mark in `components/Logo.tsx` draws the small variant inline; keep it in step.

## SEO

Each page exports `pageMetadata(pages.x)` (`lib/seo.ts`): title, description, canonical URL, Open
Graph and Twitter cards; its preview image is the `opengraph-image.png` next to it. Subpages get
a visible breadcrumb and a BreadcrumbList; the home and download pages describe the app
(SoftwareApplication), the FAQ page its questions (FAQPage). Next.js generates `robots.txt`,
`sitemap.xml` (every page, screenshots as image entries) and `manifest.webmanifest` from `app/`. With
a custom domain attached, the `*.vercel.app` address answers with `X-Robots-Tag: noindex`, so
only your domain gets indexed.

## Security, analytics and plain-text files

- `next.config.ts` sends security headers in production: a Content Security Policy (this site
  only; inline scripts allowed because static Next.js pages need them), HSTS, nosniff, DENY
  framing, a strict referrer policy, Permissions-Policy and COOP. Previews also allow Vercel's
  toolbar. If you add a third-party script or font, add its origin to the CSP there.
- Vercel Web Analytics (`<Analytics />` in `app/layout.tsx`) counts page views without cookies;
  its script comes from the site itself (`/_vercel/insights`). Turn it on in the Vercel project
  under **Analytics**, or the script answers 404. The privacy page describes it.
- `app/llms.txt/route.ts` and `app/.well-known/security.txt/route.ts` are generated from the
  same data as the pages at build time. security.txt expires a year after the build, so deploy
  at least once a year.
- Text colors are checked against WCAG AA (4.5:1). `--faint` is the lightest text allowed;
  don't make it lighter.
- The accessibility page shows the app's themes as measured by `../scripts/check-contrast.mjs`
  (`lib/themes.json`, from `npm run themes`) and one screenshot per theme
  (`public/screens/theme-<id>.webp`, from `npm run screens themes`). Redo both after a color in
  `../ui/themes.css` changes.

## Screenshots

`npm run screens` opens `../ui/index.html` in headless Edge with the live demo's stand-in for
Tauri (`demo/backend.js`), answering from the English demo mailbox (`scripts/demo-mailbox.json`:
two accounts with identities, rules, conversations, attachments, an HTML newsletter, and the mail
that "arrives" in the live demo), plays a short scene for each shot (open a reply, type in the
quick filter, …) and saves light and dark versions. The clock is fixed at 10.10.2026 09:30 so list
dates stay the same. Scenes are at the top of `scripts/screens.mjs`. The stand-in copies what the
core does for lists and filters (`list.rs`), replies (`drafts::start`), HTML mail (`html::render`,
`colors.rs`) and rules (`filters.rs`); when those change visibly, change it too. (The core's own
`sample.json` is Polish and only for its tests.)
`npm run screens reply og` retakes only those; `og` makes the preview image of every page in
`lib/pages.ts` (its `ogTitle` next to its `ogScreen`).
Use `npm run screens -- og:history` to regenerate only the history page's editorial preview.

## Deploying on Vercel

1. Import the GitHub repo in Vercel and set **Root Directory** to `site`. Everything else is
   detected (Next.js, `npm install`, `npm run build`).
2. Add the domain under **Settings → Domains**. The site picks up the production domain on its own
   (`VERCEL_PROJECT_PRODUCTION_URL`) for canonical links, the sitemap and link previews.
3. Pushes to `main` that don't touch `site/` are skipped (`vercel.json`, `ignoreCommand`), so app
   commits don't rebuild the website.

Optional environment variables:

| Variable               | Default               | Use                                           |
|------------------------|-----------------------|-----------------------------------------------|
| `NEXT_PUBLIC_SITE_URL` | Vercel's production URL | Force the canonical URL                     |
| `TELEX_RELEASES_REPO`  | `lucco669/telexmail`  | Repo whose GitHub Releases hold the installers |
| `GITHUB_TOKEN`         | –                     | Only raises GitHub's API rate limit           |
| `NEXT_PUBLIC_CONTACT_EMAIL` | `admin@telexmail.app` | Overrides the contact address on the privacy page |

## Making the download button live

Until a release exists the button says "Coming soon". It switches to a direct download link as
soon as the releases repo has a published release with a Tauri installer attached
(`Telex_<version>_x64-setup.exe`, plus the `.msi` as a second link), within an hour, with no
redeploy. The repo has to be **public**: visitors can't download assets from a private repo's
releases. If `telexmail` stays private, make a public repo just for installers (for example
`telex-releases`) and set `TELEX_RELEASES_REPO` to it.

The release workflow makes a **draft** release, and GitHub hides drafts from everyone else, the
site included: the button stays "Coming soon" until you press **Publish release** on GitHub.
"Within an hour" means the first visit after the hour starts a rebuild of the page in the
background (`cacheLife` in `lib/release.ts`: revalidate after an hour, never expire), and the
visits after that see the new release. Set `GITHUB_TOKEN` in Vercel to be safe: without it the
lookup shares GitHub's limit of 60 requests an hour with everything else on Vercel's IP address.

When GitHub can't be asked (refused, unreachable), the lookup throws on the live site: the page's
background refresh fails, Next.js keeps serving the page with the last good answer and tries again
on the next visit, so a failure never turns the downloads into "Coming soon". At build time and in
`npm run dev` there is no earlier answer, so the site offers `lib/known-release.ts` (with a note on
the download page that it couldn't check for a newer one), or, if that is empty, links to GitHub's
newest-release page. "Coming soon" is only for when GitHub answers that nothing is released.
